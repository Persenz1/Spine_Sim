# M0 提示词：公共基础与运行骨架

## 一、任务身份

你负责重构爪刺耦合仿真器的 M0。M0 是整个项目的公共基础和运行骨架，但不包含地形生成、接触力学、阵列求解或十字对爪平衡。

本任务面向实际代码仓库执行，不是只写设计说明。你需要先审查现有仓库，再实现、测试并交付可供 M1–M4 直接使用的基础层。

## 二、权威文件和冲突顺序

开始前完整阅读：

1. `03_爪刺耦合仿真器_工程背景_理论边界与实现指导_执行版.md`；
2. `04_爪刺仿真器_失败问题总结与重启约束.md`。

冲突时：

- 工程范围、模块职责和新接口以 03 执行版为准；
- 旧代码禁用项、旧结果状态和失败语义以 04 为准；
- 旧仓库代码只能作为可复用资产候选，不能反向定义需求。

禁止覆盖旧生产结果和旧 9,600-case 工作区。必要时建立新分支、新命名空间或新结果根目录。

## 三、M0 的目标

建立一个轻量、确定、跨 Windows/Linux、可断点恢复的 Python 基础层，使后续模块能够：

- 使用统一 SI 单位和坐标；
- 生成稳定 ID 和 hash；
- 读取版本化配置；
- 分离物理、数值、模型和运行状态；
- 安全保存逐步结果和事件；
- 运行单 case、批量 campaign 和恢复未完成任务；
- 在无 GPU 环境完整工作；
- 在有 GPU 时把后端能力显式传给 M1；
- 让 Codex 后续直接读取稳定数据做统计和绘图。

M0 不追求通用仿真平台，不建设 UI、数据库、远程队列、自动 Schema 迁移或复杂事务系统。

## 四、必须完成的工作

### 4.1 仓库审查和迁移清单

先输出一份简短审查：

- 当前目录结构；
- 可直接复用的单位、坐标、ID、结果读写和并行代码；
- 只能逐项参考的旧状态事务、Bundle、Schema 和资源调度代码；
- 必须停用的旧 `preload_infeasible` 业务语义和旧生产 runner；
- 新代码放置位置和与旧代码的隔离方式。

不得为了兼容旧代码而扭曲新接口。

### 4.2 单位、坐标和 wrench

实现并测试：

- SI 输入归一化；
- 全局和单元局部坐标元数据；
- 向量、旋转矩阵、参考点和作用对象标签；
- 六维 wrench；
- wrench 旋转与参考点搬移；
- 明确的正号和对象命名，例如 `spine_on_plate`、`wall_on_unit`。

禁止只保存六个无元数据浮点数。

### 4.3 配置模型

建立最小版本化配置结构：

- `ProjectConfig`；
- `BackendConfig`；
- `TerrainRecipeRef` 和 `TerrainRegionSpec` 的公共 Schema；
- `M2CaseSpec`、`M3CaseSpec`、`M4CaseSpec` 的基础协议或数据类；
- `CampaignSpec`；
- 数值容差和路径参数；
- 明确的单位检查和范围检查。

配置文件可使用 YAML 或 JSON，但读入后必须归一化为 SI，并保存原始配置和归一化配置。

### 4.4 ID、hash 和 lineage

实现确定性标识：

- `terrain_recipe_id`；
- `region_id`；
- `track_id`；
- `case_id`；
- `campaign_id`；
- `module_version`；
- `config_hash`；
- `upstream_hash`。

要求：

- 相同规范化输入生成相同 ID；
- 参数次序和 YAML 排版差异不改变 ID；
- 代码/算法版本变化可显式产生新结果身份；
- lineage 足以追踪 M1→M2→M3→M4，但不要建设复杂血缘图数据库。

### 4.5 状态、事件和错误

至少分离：

```text
physical_state
numerical_state
model_state
run_state
```

建立结构化事件：

- 接触、脱离、再接触；
- 滑移起始；
- 硬限位；
- 地形出界；
- 数值重试和失败；
- 取消和恢复。

M0 只定义结构，不决定物理事件成立条件。

错误必须区分：

- 输入/配置错误；
- 模型未闭合；
- 数值未收敛；
- 执行异常；
- 用户取消。

禁止把异常统一转换为 `physical_infeasible`。

### 4.6 结果格式

建立稳定但轻量的写入工具：

```text
campaign/
├── manifest.json
├── config/
├── cases.parquet
├── paths/
├── events.parquet 或 events.jsonl
├── validation.json
└── lineage.json
```

单 case 必须支持：

- 原子临时文件写入后重命名；
- 结果完成标记；
- 失败时保存已有诊断；
- 不完整文件识别；
- 只读加载；
- 对逐步数组使用 NPZ/Parquet 等适合格式。

不要为未稳定字段建立复杂自动迁移系统。

### 4.7 运行器

提供最小命令行入口或等效 Python API：

- 验证环境；
- 运行单 case；
- 运行小 campaign；
- 运行正式 campaign；
- 恢复未完成 campaign；
- 只重跑失败 case；
- 汇总运行状态。

并行原则：

- 独立 case 或 seed 级多进程；
- 不在单个顺序状态机内部强行并行；
- Windows `spawn` 和 Linux 进程模型均测试；
- worker 数可配置；
- 记录墙钟时间、峰值 RAM/VRAM 和阶段耗时；
- 一个 case 失败不能破坏其余 case。

### 4.8 后端能力

建立统一后端发现：

- CPU 永远可用；
- NVIDIA/CUDA 为可选能力；
- 后端选择显式记录；
- M0 不要求安装 CUDA 才能运行；
- 不实现跨 GPU 通信；
- M1 可查询可用后端，但 M0 不生成地形。

## 五、目录和依赖要求

优先保持结构简单。可以根据现有仓库调整，但概念上应分离：

```text
src/
├── core/
├── io/
├── runtime/
├── validation/
└── cli/
```

避免：

- 万能 `BaseModule`；
- 过深继承；
- 全局可变单例；
- 隐式单位转换；
- 用异常字符串代替结构化状态；
- 为未来 UI 预留大量空接口。

## 六、测试和验收

至少完成：

1. SI 单位和非法范围测试；
2. 坐标旋转和 wrench 搬移手算测试；
3. 配置规范化和 hash 确定性；
4. 同输入 ID 完全一致；
5. 状态维度不能被非法混合；
6. 原子写入、中断文件识别和断点恢复；
7. Windows/Linux 路径无硬编码；
8. 单 worker 与多 worker 结果 hash 一致；
9. 单 case 执行异常不影响其他 case；
10. 无 GPU 环境完整通过；
11. 有 GPU 时后端发现和记录正确；
12. 一个最小假模块能通过 M0 runner 保存和恢复。

测试数量不是验收指标。必须给出为何这些测试覆盖了 M0 的风险。

## 七、禁止项

- 不实现 M1 地形生成；
- 不实现任何接触、摩擦、弹簧或梁公式；
- 不复用旧 `preload_infeasible` 作为通用失败；
- 不建立 M5/M6；
- 不做 UI、安装包、云同步和数据库；
- 不在物理模块完成前做性能大优化；
- 不覆盖旧结果；
- 不用全链跑通代替模块验收。

## 八、交付物

完成后必须交付：

1. M0 源代码；
2. 测试及测试报告；
3. 最小示例配置；
4. CLI/API 使用说明；
5. 结果字段数据字典；
6. 旧资产复用/停用清单；
7. `M0_to_M1_handoff.md`，明确 M1 可用的配置、ID、文件和后端接口；
8. 未闭合问题列表。

最终报告必须说明：

- 哪些旧代码被复用；
- 哪些被隔离；
- M0 是否在 CPU-only Windows/Linux 环境可运行；
- 哪些接口已冻结；
- M1 开始前是否存在阻塞问题。
